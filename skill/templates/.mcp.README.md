# `.mcp.json` — MCP server configuration

The template ships with an **empty `mcpServers`** object. This is deliberate: shipping example server entries risks two failure modes.

1. **Copy-paste servers that don't authenticate** — a stub `github` MCP entry that requires a token no one has configured produces a noisy failure on session start, and teams silently start ignoring the file.
2. **Copy-paste servers that authenticate against someone else's account** — worse.

## What to do

Pick the MCP servers your team uses and add them here. Common patterns:

```jsonc
{
  "mcpServers": {
    "github": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-github"],
      "env": {
        "GITHUB_PERSONAL_ACCESS_TOKEN": "${GITHUB_TOKEN}"
      }
    },
    "context7": {
      "type": "sse",
      "url": "https://mcp.context7.com/sse"
    },
    "postgres": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres", "${DATABASE_URL}"]
    }
  }
}
```

Notes:

- **Use env-var references (`${VAR}`)** for secrets, never inline tokens.
- Match each entry with a line in `AGENTS.md`'s Project Overview describing what the server provides and when the agent should use it.
- If the team decides to use no MCP servers, that is fine — just declare it in `AGENTS.md` (D04 passes on either `.mcp.json` present OR an explicit no-MCP declaration).

## Adding a server later

The `bootstrap.sh` interactive flow (T-27) offers `.mcp.json` templating separately from the other templates because MCP configuration is intrinsically per-team. If a target repo already has a working `.mcp.json`, bootstrap will skip it by default — you can always re-run with `--apply --template=.mcp.json` to explicitly overwrite.
